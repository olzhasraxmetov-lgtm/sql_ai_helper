# 0004. Журнал вопросов — в отдельной схеме `app`, магазин — в схеме `shop`

**Статус:** принято, 2026-10-22

## Контекст
Сервис ведёт журнал вопросов (вопрос, сгенерированный SQL, стоимость, итог). SQL, который
пишет LLM, не должен иметь доступа к журналу: иначе вопрос «покажи последние вопросы»
вернёт чужие вопросы.

## Решение
- Таблицы магазина — в схеме `shop`, таблицы сервиса — в схеме `app`, в одной базе.
- Роли:
  - `llm_readonly` — `USAGE` и `SELECT` только на `shop`, без `USAGE` на `app`; `search_path = shop`;
  - `app_service` — запись и чтение в `app`;
  - `migrator` — владелец обеих схем, под ним работает Alembic.
- Обе схемы ведутся одной цепочкой миграций Alembic.
- В промпт LLM попадает только схема `shop`.

## Последствия
- Доступ к журналу закрыт правами БД, а не инструкцией в промпте.
- Текущий `db/bookstore_schema.sql` описывает таблицы без схемы `shop`; перенос делается
  миграцией, файл обновляется выгрузкой `pg_dump --schema-only`.
- Права по умолчанию (`ALTER DEFAULT PRIVILEGES`) нужны, чтобы новые таблицы в `shop`
  автоматически были доступны `llm_readonly`, а в `app` — нет.

## Отвергнуто
- Отдельная база — две цепочки миграций и два пула ради одной таблицы.
- Журнал в `public` + `REVOKE` — держится на том, что каждую новую таблицу не забудут закрыть.
