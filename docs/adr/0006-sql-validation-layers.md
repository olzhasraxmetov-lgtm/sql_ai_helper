# 0006. Проверка SQL — sqlglot как первый фильтр, права БД как основная защита

**Статус:** принято, 2026-10-22

## Контекст
SQL пишет LLM, и злонамеренный или просто неудачный вопрос может привести к запросу,
который меняет данные, читает служебные таблицы, висит бесконечно или меняет настройки сессии.

## Решение
Слои защиты, от раннего к позднему:
1. **sqlglot** (до выполнения, итог `rejected` с понятной причиной):
   - ровно один оператор;
   - верхний оператор `SELECT` или `WITH … SELECT`; в дереве нет `INSERT/UPDATE/DELETE`/DDL, включая CTE;
   - только таблицы схемы `shop`;
   - список запрещённых функций: `pg_*`, `set_config`, `current_setting`, `dblink*`, `lo_*`.
2. **Роль `llm_readonly`** — только `SELECT` на `shop`, без доступа к `app`, без суперпользователя.
3. **Транзакция `readonly=True`**, всегда завершается `ROLLBACK`: так откатываются и изменения
   настроек сессии, если они проскочили.
4. **`statement_timeout`** через `server_settings` подключения.
5. **Лимит строк**: результат читается курсором, берётся N+1 строка (N = 500); запрос не
   переписывается. Если строк больше N — флаг `truncated`. В объяснение LLM уходят первые
   50 строк, имена колонок и флаг `truncated`.

## Последствия
- Запрещённые функции дают ранний и понятный отказ, а не невнятный `execution_error`.
- Список запрещённых функций короткий, поэтому нормальные запросы почти не отклоняются ложно.
- `set_config` запрещён отдельно: `statement_timeout` может поменять любая роль для своей сессии,
  и права на таблицы от этого не защищают.

## Отвергнуто
- Список разрешённых функций — ложные `rejected` на законных функциях портят метрику точности.
- Без проверки функций — атаки неотличимы в журнале от ошибок модели.
