# Text-to-SQL по базе книжного магазина — контекст проекта

## Цель
Портфолио-проект: владелец интернет-магазина книг задаёт вопрос обычным языком
(«какой жанр принёс больше всего денег в сентябре?»), LLM пишет SQL, сервис безопасно
выполняет его на PostgreSQL, LLM объясняет результат.
Следующий проект на той же базе — AI-аналитик продаж (выгрузка → SQL-метрики → выводы LLM).

Предыдущий проект автора: Telegram-бот записи к барберу (aiogram 3, чистая архитектура,
SQLite + Alembic, mypy strict, CI, Docker). Здесь закрываем пробелы: реальный AI внутри,
PostgreSQL, веб-часть.

## План (≈20 ч/неделю)
1. **База и каркас** — схема (✅ готова), генерация данных (⏭ следующий шаг), FastAPI + PostgreSQL в docker compose, слои как в боте.
2. **Безопасность выполнения** (до подключения LLM) — read-only роль PostgreSQL, `statement_timeout`, лимит строк, разбор запроса (например, sqlglot).
3. **LLM** — промпт: схема + правила домена + few-shot примеры; цепочка вопрос → SQL → проверка → выполнение → объяснение; одна попытка самоисправления по ошибке; показывать сгенерированный SQL.
4. **Оценка и упаковка** — 30–40 вопросов с эталонным SQL и ожидаемым ответом, метрика точности, интерфейс (веб или Telegram), README.

## Схема (PostgreSQL) — файл `db/bookstore_schema.sql`
Таблицы: `genres`, `authors`, `users`, `promocodes`, `books`, `book_author`,
`orders`, `order_item`, `payments`, `refunds`.

Ключевые решения:
- **Позиции заказа** — `order_item (order_id, book_id, unit_price, quantity)`, `UNIQUE (order_id, book_id)`.
- **Цена:** `books.price` — текущая цена каталога; `order_item.unit_price` — цена за 1 шт., зафиксированная в момент заказа. Выручка считается только по `unit_price`.
- **Авторы:** многие-ко-многим через `book_author`, PK = `(book_id, author_id)`.
- **Жанр:** одна книга = один жанр (`books.genre_id`).
- **Издания** (твёрдая/мягкая обложка) — в v1 не моделируем: одна строка `books` = один товар.
- **Промокоды:** фиксированная сумма в ₸. `promocodes.discount_sum` — текущая скидка; `orders.discount_per_order` — скидка, зафиксированная в заказе (на весь заказ). `promocode_id` = NULL, если промокода нет; `discount_per_order` NOT NULL DEFAULT 0; CHECK: скидка без промокода запрещена.
- **Статусы:**
  - `orders.status`: `pending`, `confirmed` (магазин принял заказ в работу), `cancelled`;
  - `payments.status`: `pending`, `succeeded`, `failed`. Возвратов в статусах нет — они только в `refunds`.
- **Платежи:** `created_at` — начало попытки, `paid_at` — момент успешной оплаты (CHECK: заполнен тогда и только тогда, когда `succeeded`). Частичный уникальный индекс: не больше одного `succeeded`-платежа на заказ.
- **Возвраты:** `refunds (order_item_id, quantity, reason, refunded_at)` — привязаны к позиции, можно вернуть часть экземпляров; сумма = `refunds.quantity × order_item.unit_price`.
- Деньги — `numeric(12,2)`; моменты событий — `timestamptz`; `birthdate` — `date`.
- Индексы на внешние ключи и на `payments.paid_at`, `refunds.refunded_at`.
- На уровне приложения (не схемы): скидка не больше суммы заказа; возвращено не больше, чем куплено.

## Эталонный запрос №1 — «Какая выручка за март 2026?»
```sql
WITH revenue AS (
    SELECT
        o.id AS order_id,
        SUM(oi.unit_price * oi.quantity) - o.discount_per_order AS order_revenue
    FROM payments p
    JOIN orders o      ON o.id = p.order_id
    JOIN order_item oi ON oi.order_id = o.id
    WHERE p.paid_at >= '2026-03-01'
      AND p.paid_at <  '2026-04-01'
      AND p.status = 'succeeded'
      AND o.status = 'confirmed'
    GROUP BY o.id
),
march_refunds AS (
    SELECT COALESCE(SUM(r.quantity * oi.unit_price), 0) AS refunds_amount
    FROM refunds r
    JOIN order_item oi ON oi.id = r.order_item_id
    WHERE r.refunded_at >= '2026-03-01'
      AND r.refunded_at <  '2026-04-01'
)
SELECT
    (SELECT COALESCE(SUM(order_revenue), 0) FROM revenue)
  - (SELECT refunds_amount FROM march_refunds) AS march_revenue;
```
Ловушки, которые он проверяет (обязательно включить в тестовый набор):
1. Скидка размножается при JOIN заказа с позициями — вычитать вне SUM / после агрегации.
2. Неудачный платёж перед успешным — без фильтра по статусу заказ считается дважды.
3. `confirmed`-заказ без успешного платежа (оплата идёт или не прошла) не входит в выручку —
   одного фильтра по статусу заказа мало. Успешный платёж бывает только у `confirmed`
   (см. `docs/sql-rules.md`, «Статусы»).
4. Граница периода: платёж в 23:50 31 марта — март; ровно в 00:00 1 апреля — апрель (`<`, не `<=`).
5. Возвраты по дате возврата; пустой месяц без возвратов — SUM даёт NULL → COALESCE.
6. Выручка по авторам: книга с двумя авторами засчитывается каждому — сумма по авторам больше общей выручки (см. `docs/sql-rules.md`, «Авторы и жанры»).

## Следующий шаг — генерация данных
Python-скрипт (Faker) → PostgreSQL. Нужны закономерности, а не равномерный шум:
масштаб (например, ~2 000 клиентов, ~300 книг, ~10 000 заказов за 2 года), сезонность
(сентябрь, декабрь), хиты (≈20% книг дают большую часть продаж), повторные покупатели,
доли отмен / неудачных платежей / возвратов, города Казахстана с разными весами,
промокоды на часть заказов. Плюс специально заложенные пограничные случаи из списка ловушек.
